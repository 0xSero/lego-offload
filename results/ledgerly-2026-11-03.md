## Findings

1. **The identifier scan fails open, and the failure is cached.** The vault learns names from each private file by
   asking the local model to list identifiers (`transport.find_ids`). On T-1004 that call hit the 12,000-token cap
   (`finish_reason: length`, empty output) because the model worked on the base64 block; `_find` turned the truncated
   reply into "no identifiers", `scrub.Vault.learn` stored the file's hash as learnt, and the door served the file at
   `scrubbed` with only the regex rules. The email was masked; "From: Barnaby Featherstonehaugh" was not, and reached
   Opus in clear. No later session rescans the file. Any file that makes the scan fail (a blob, a huge table, a model
   timeout) is protected by patterns alone, silently. The fix is to treat a non-`stop` finish or a parse failure as
   unknown: refuse the file at `scrubbed` until a scan completes, and do not record the hash.
2. **Local model quality held up here.** Every typed answer Qwen gave in the five tasks was right: the incident
   question, the six config booleans, the duplicate-group count and the account-id check. The one wrong answer of the
   whole trial was yesterday's demo (Research, 143), caused by the schema being absent from its prompt, fixed since.
   An earlier draft of this note called the dedupe count a miscount; the mistake was in my expected answer.
3. The scrubber masked every name, email, phone, address, IP and session id in the other 13 scrubbed files and in the
   omp relay. Dates and order ids cross, as documented.
